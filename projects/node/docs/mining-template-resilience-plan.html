Mining Template Resilience Plan

This branch moves a watchdog workaround into source: the node should know when a template is usable, when the last build failed but the last-good template is still safe, and how to keep pool subscribers on the newest template without building an unbounded backlog.

Source-level reliability No live service changes Mining hot path Consensus-adjacent safety

Problem

Template Build Failure Is Too Strong

buildTemplateHealthResult currently treats a recent build error as non-mineable even when a previously built template may still be fresh and safe. This makes routing and watchdog behavior overly reactive.

Template Work Is Not Latest-Only

Mempool changes can request template rebuilds repeatedly. Parent/tip changes matter, but ordinary mempool churn should be coalesced so the node does not waste CPU building stale intermediate templates.

Slow Subscribers Can Back Up Delivery

The subscription comment says slow subscribers are handled by buffering, but event.Feed.Send waits for subscriber channels. The WebSocket layer needs explicit latest-only delivery so a slow pool cannot hold up emission.

Target Behavior

1. Trigger

Classify template requests as parent/tip, forced, coinbase/pow change, mempool, TTL, or stall recovery.

2. Coalesce

Allow only one active build. Preserve the latest pending request and promote parent/tip changes above mempool churn.

3. Build

Build a new template once. Record duration, reason, and error code without destroying a still-valid last-good template.

4. Validate

Serve last-good only while parent set, coinbase/pow, sync state, timestamp, and TTL remain safe.

5. Emit

Emit latest template snapshots to subscribers with drop-oldest semantics for slow clients.

Implementation Slices

SliceChangeSafety RulePrimary Tests
A. Health semantics Add explicit fields for last_good_template, last_good_age_ms, and last_build_error_is_blocking. Build errors do not imply non-mineable unless no valid last-good template exists. Health result with prior template plus transient build failure remains mineable.
B. Template validity helper Extract a pure helper that evaluates parent equality, template age, coinbase, pow type, and sync allowance. Never serve last-good after parent/tip change or expiry. Expired and parent-mismatch templates are rejected with clear reasons.
C. Latest-only queue Introduce a small build scheduler that coalesces non-critical rebuild requests and records the latest pending reason. Parent/tip changes outrank mempool churn and cannot be lost. Burst mempool requests produce one pending build; parent change during burst wins.
D. Subscriber delivery Use a latest-only subscription bridge for BlockTemplate WebSocket clients. A slow subscriber must not block template emission for the miner. Slow subscriber receives the newest sequence and old pending pushes are dropped.

Definition Of Done

  • Template health distinguishes last build error from current template mineability.
  • Slow WebSocket subscribers cannot block template emission.
  • Mempool-triggered rebuild bursts are latest-only and bounded.
  • Parent/tip changes are never coalesced away behind mempool churn.
  • Tests pass for miner, mining, and RPC command packages.
  • PR body documents that live deployment and A/B testing are separate approval steps.
