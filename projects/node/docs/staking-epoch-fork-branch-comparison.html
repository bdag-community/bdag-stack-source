Staking Epoch Fork Mitigation Branch Comparison

This report compares main with fix/consensus-evm-state-guard for the current mainnet fork problem: some nodes derive staking epochs from timestamps while others derive them from block height, causing different staking reward/tally state and therefore different EVM block hashes.

Bottom Line

main matches the stated intent. It keeps mainnet staking epoch calculation timestamp-based and adds a P2P EVM checkpoint gate so peers must advertise a safe EVM hash and state root roughly 5,000 EVM blocks behind their head.

fix/consensus-evm-state-guard keeps the same timestamp epoch calculation, but it does not implement the P2P "show a hash 5k before tip" compatibility gate. Its main addition is a local EVM state guard that is useful as a hardening layer only when all nodes are configured consistently.

Main Risk In Fix Branch

The fix branch changes staking reward split selection to read and write a local DB sidecar keyed by epoch. That state is not in the block, so stale or divergent local DB values can create exactly the kind of node-local consensus divergence this incident is trying to remove.

Problem Model

The fork occurs when two nodes process the same native block sequence but compute a different staking epoch. A timestamp-based node rotates chain tally and staking reward state when (header.Time - genesisTime) / epochSeconds crosses the boundary. A block-height-based node rotates at header.Number / interval. Around boundaries, these can disagree even with the same transactions.

Once the epoch differs, staking tallies, auto-stake accounting, miner/staker rewards, and resulting EVM state root can diverge. The network then needs both a canonical rule and a way to stop syncing from peers that are already on the other rule.

Resolution Flow

main: canonical epoch plus peer quarantine

1. EpochMainnet uses timestamp duration.
2. EVM stateRewards and tallies produce deterministic EVM header.
3. Safe pointAdvertise EVM head minus 5,000.
4. P2P gateReject missing, old, or mismatched checkpoint peers.
5. ImportUse peer checkpoint while processing blocks from that peer.

fix/consensus-evm-state-guard: local guard path

1. EpochMainnet also uses timestamp duration.
2. SplitMay use local epoch-split sidecar before on-chain state.
3. GuardDry-run EVM block if guard enabled.

5. Peer actionDisconnect peer after guard rejection.

Operational Consequences

Using main

  • Nodes converge on timestamp-based staking epochs for mainnet.
  • Old protocol peers and peers missing the EVM checkpoint are rejected.
  • Peers on a height-based fork should fail the EVM checkpoint hash/root comparison once local history is known.
  • Rollout requires enough v46 peers to avoid isolating upgraded nodes from the network.

Using the fix branch as-is

  • Timestamp epoch calculation is present, so nodes on this branch should not use height logic for mainnet.
  • There is no handshake-level proof that a peer is on the same timestamp-based EVM history.
  • The guard is off unless configured, except if a future params-level commitment start order is set.
  • The epoch split sidecar can create node-local reward split divergence.

Recommendation

Use main as the base for the current incident response. It implements the intended solution: canonical timestamp-based mainnet staking epochs plus P2P rejection of peers that cannot present the safe EVM checkpoint derived from that rule.

If the EVM state guard work from fix/consensus-evm-state-guard is still desired, port it as a separate hardening layer after the network checkpoint solution is preserved. Before porting, remove or redesign the local epoch miner-split sidecar so consensus-critical reward split remains derived from block/state data that every node can reproduce.

Do not replace main's P2P checkpoint path with the fix branch. The fix branch is a local validation mechanism, not the requested network quarantine mechanism.
